# PRD 与 Design 规划合同强化

## 目标

1. 让用户只读 `prd.md` 就能快速分辨本次新增、修改、删除、保持不变及产品边界，并能从编号追踪到用户可见结果。
2. 将 UI 原型、交互变化、轻量/复杂任务判定和数据库设计要求从文字建议升级为可检查的规划合同，阻止不完整规划进入实施阶段。
3. 保持 PRD 面向产品阅读；技术边界、数据模型和实现方案继续下沉到 `design.md`，执行步骤继续放入 `implement.md`。

## 需求

### R1 新增

- **R1.1 规划画像**：新 Task 必须显式回答交互、数据模型、公共合同、跨层、状态生命周期、安全/兼容/发布和技术取舍是否发生变化；系统据此推导 `lightweight` 或 `complex`，不得只由 Agent 自由判断。
- **R1.2 交互变化图**：流程图通常可选；当规划画像声明交互功能改变时，PRD 必须补充 Mermaid 交互图，并用文字和红色样式标出新增、修改或删除的流程节点与连线。
- **R1.3 数据库设计合同**：当规划画像声明数据模型改变时，`design.md` 必须给出 DDL、表用途和全部字段备注；ER 图保持可选。
- **R1.4 规划状态检查**：提供只读状态入口，集中报告规划画像、PRD 结构、UI 原型、交互图、复杂任务产物及数据库设计合同是否满足要求。

### R2 修改

- **R2.1 UI 原型可见性**：`meta.ui=true` 的 Task 必须在 PRD“用户可见结果”中包含当前 prototype 主入口、预览、摘要和批准状态；原型缺失、待批准、摘要过期或 PRD 引用不一致时禁止 `task.py start`。
- **R2.2 需求表达**：PRD“需求”按实际存在的变更类型分组；组使用 `R1`、`R2` 编号，组内改动使用 `R1.1`、`R1.2` 等稳定编号，不生成空类型。
- **R2.3 结果映射**：“用户可见结果”中的每个结果使用 `O1`、`O2` 编号，并引用对应需求编号；技术细节不能为了编号重新塞回 PRD。
- **R2.4 启动门禁**：`task.py start` 在写状态、活动指针或触发生命周期 hook 前统一执行规划合同与既有 prototype 摘要批准检查，失败必须无副作用并给出可操作修复项。

### R3 保持不变

- **R3.1 核心结构**：PRD 仍按“目标 → 需求 → 用户可见结果”排列；目标使用有序列表，用户可见结果使用检查清单。
- **R3.2 原型生命周期**：保留 session `019fb7d3-6ab2-7772-b223-c0330adcae85` 已实现的 `prototype/manifest.json`、摘要绑定批准和 start 前硬门禁，不重写为仅靠文档提醒的软规则。
- **R3.3 兼容边界**：没有新规划合同版本标记的历史 Task 保持原行为；不得扫描标题或自然语言猜测是否为 UI、交互或数据库 Task。
- **R3.4 合并边界**：父仓库按 `cooker-code/Trellis` 自身验证结果推进；`mindfold-ai/marketplace` 与 `mindfold-ai/docs` 的外部 PR 不作为合并门禁。

## 用户可见结果

- [ ] **O1（R2.1）** 用户打开任一 UI Task 的 PRD，能直接找到当前 prototype 入口、静态预览、摘要和 `pending_user_approval`/`approved` 状态；缺少这些内容时不能开始实施。
- [ ] **O2（R2.2、R2.3）** 用户能通过 `R1.1`、`R2.1`、`O1` 等编号快速区分每类改动并追踪到对应结果，不需要从长段落中猜重点。
- [ ] **O3（R1.2）** 普通 PRD 不被强制加入装饰性流程图；交互功能改变时，用户能从图中直接看出哪条流程被新增、修改或删除。
- [ ] **O4（R1.1、R2.4）** 用户能看到 Task 被判为轻量或复杂的明确理由；复杂 Task 缺少 `design.md`/`implement.md`、画像未决或合同不完整时，启动会被拒绝且无副作用。
- [ ] **O5（R1.3）** 用户阅读涉及数据库改动的 `design.md` 时，能看到每张表的用途、每个字段的类型和业务含义；ER 图可按关系复杂度选择加入，不作为统一硬门禁。
- [ ] **O6（R3.2、R3.3）** 已有 UI 原型摘要批准能力继续有效，历史 Task 不因升级被无差别阻塞。

## 范围外

- 不在本 Task 中提交、合并或发布 session `019fb7d3-6ab2-7772-b223-c0330adcae85` 的既有未提交实现；它是本 Task 的前置本地基线，需要单独完成交付闭环。
- 不使用 LLM 或关键词扫描自动猜测规划画像。
- 不强制所有 PRD 都有交互图，也不强制所有数据库设计都有 ER 图。
- 不要求 PRD 列出源码文件、Schema、API 参数或执行命令。
