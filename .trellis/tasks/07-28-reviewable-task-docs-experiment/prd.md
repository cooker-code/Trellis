# 可读任务文档与对照指标实验

## 目标

让 Trellis 在不降低需求完整性、验收质量和 Agent 执行正确率的前提下，提供一种更适合人快速审阅的任务文档模式，并能与现有原生模式进行可重复、可量化的对照。

用户价值是：打开 Task 后能快速回答“做什么、不做什么、当前到哪一步、已经确认了什么、哪些规则不能破坏、如何证明完成”，无需先读完 Agent 的研究过程和技术执行清单。

## 已确认事实

- 当前 `task.py create` 生成的 PRD 只有 Goal、Requirements、Acceptance Criteria 和 Notes 骨架，没有人类审阅层与 Agent 细节层的显式边界。
- `prd.md` 应记录已收敛的需求和决策；阻塞性产品决策应在 Brainstorm 交互中逐项确认，不能把一批“待确认”问题留给最终 PRD。
- `implement.md` 当前定位为技术执行计划，但用户需要的是以交付结果、完成证据和门禁组织的可见路线，而不是只看到文件、函数和命令清单。
- 项目已有 benchmark 先例，可采集 input/output/cache Token、工具调用、耗时并进行重复试验；本任务应复用该实验纪律。
- 当前工作在独立分支 `codex/reviewable-task-docs-experiment` 和 worktree `/Users/blank/wangliang/gitcode/Trellis-reviewable-docs` 中完成，不包含原工作树的未提交修改。

## 需求

### R1：保留原生模式

- 默认行为继续生成现有 Trellis 原生文档，避免静默改变所有用户的工作流。
- 用户创建 Task 时可以显式选择 `reviewable`（可审阅）文档模式。
- Task 必须记录实际使用的模式，使后续指标能够正确归组。

### R2：可审阅 PRD

`reviewable` 模式的 PRD 必须：

- 第一屏优先呈现一句话结果、范围内、范围外、已确认决策、不可破坏规则和成功标准。
- 不在最终 PRD 中保留已解决问题或普通“待确认”决策表。
- 使用明确标记区分“用户审批面”和后续详细需求，便于稳定测量审批阅读量。
- 首次出现必要专业术语时提供中文含义或本任务语义；不强制生成无关术语表。

### R3：结果型实施路线

`reviewable` 模式的实施计划指导必须：

- 先以“阶段、用户得到的结果、完成证据、状态/门禁”表达交付路线。
- 将文件、函数、命令等 Agent 技术步骤放在详细执行区，不能用它们替代用户可见路线。
- 保持 `implement.md` 的执行计划职责，不在 PRD 中混入实现清单。

### R4：Ponytail 文档复杂度策略

Brainstorm 和 Check 指导必须加入最小的文档复杂度判断：

1. 用户是否需要依靠该内容做决定？
2. 能否用表、关键图或不变量更清楚地表达？
3. 仅供 Agent 执行的细节是否应下沉？
4. 仅作审计的证据是否应放入 `research/`？
5. 删除后若不影响决策、执行或验收，是否应删除？

这套策略不得删除用户明确要求、安全边界、兼容性要求、验收标准或必要证据。

### R5：量化指标

提供确定性、机器可读的文档指标，至少包括：

- UTF-8 字节、字符、行数。
- 总文档 estimated Token（估算词元）。
- approval surface estimated Token（用户审批面估算词元）。
- 详细区估算词元。
- 标题、清单、未解决占位符和术语定义数量。
- 原生/可审阅两份文档的绝对差与百分比变化。

估算 Token 必须明确标注为估算，不能冒充某个模型 API 的真实计费 Token。

实验结果 Schema 还必须能够记录 runner（运行器）提供的真实 input/output/cache Token、耗时、交互轮数和正确性结果；聚合时估算值与真实值分栏。

### R6：对照实验链路

- 提供 `native`（原生）与 `reviewable` 两条可选择链路。
- 提供 `shadow`（影子）实验记录能力：同一事实输入可生成两份文档供盲审，但用户只需使用其中一份。
- 支持以 JSON/JSONL 保存任务 ID、variant（实验组）、代码基线、模型、运行编号和指标。
- 能对固定历史 Task 夹具运行离线回测；不得让实验组读取任务完成后的答案。
- 历史回测和真实任务数据分开报告；用户主动覆盖组别的样本不得混入随机实验的因果比较。

### R7：正确性护栏

- 严重需求遗漏必须为零。
- 原始需求覆盖率、验收条件和实现检查不得因文档压缩而下降。
- Token 下降不能单独判定实验成功。
- 结果报告必须同时展示阅读成本、交互成本、正确性和样本信息。

### R8：兼容性

- 中英文 Task 骨架都应支持两种模式。
- 原生模式生成内容和现有 CLI 行为保持不变。
- 不新增 Task lifecycle（生命周期）状态，不复制 Ponytail Hook 或模式运行时。
- 不要求新增模型专用 tokenizer（分词器）依赖；真实 Token 由实验 runner 的 usage（用量）数据提供。

## 验收标准

- [ ] AC1：未指定文档模式时，Task 创建结果与当前原生行为一致。
- [ ] AC2：显式选择 `reviewable` 时，PRD 包含稳定的用户审批面边界和可读骨架，Task 元数据记录模式。
- [ ] AC3：Brainstorm 会在交互阶段解决阻塞决策，最终 PRD 只保留已确认决策或延期触发条件。
- [ ] AC4：Implement 指导同时区分用户交付路线和 Agent 技术步骤；Check 能检查文档复杂度但不删正确性护栏。
- [ ] AC5：指标命令可输出文本和 JSON；同一输入重复测量结果一致。
- [ ] AC6：比较命令能输出 native/reviewable 的绝对差、比例变化和正确性护栏字段。
- [ ] AC7：实验 JSONL 能同时容纳估算文档 Token 与 runner 提供的真实 input/output/cache Token，缺失真实 usage 时明确为 null。
- [ ] AC8：至少一组固定历史 Task 夹具完成 native/reviewable 回测并生成版本化结果报告。
- [ ] AC9：回测报告包含样本、基线 SHA、运行次数、阅读 Token、审批面 Token、未解决占位符和护栏结果，不把结构指标宣称为用户理解效果。
- [ ] AC10：相关单元/集成测试、`pnpm lint`、`pnpm typecheck` 和目标 CLI 测试通过。
- [ ] AC11：GitNexus 变更检测证明影响范围符合设计；默认分支与原工作树未被修改。

## 范围外

- 本轮不验证 Ponytail 对最终代码复杂度、依赖数量或缺陷率的影响；该实验必须与文档可读性实验分开。
- 不接入付费模型 API，也不承诺在本任务中完成大规模人工理解盲测。
- 不重写已有历史 Task。
- 不新增 Web UI、远程实验服务或新的 Task 状态。
- 不把模型无关的 Token 估算值包装成精确计费 Token。

## 延期项与触发条件

- 当离线回测通过且有足够真实 Task 样本后，再评估将 `reviewable` 设为默认模式。
- 当至少有两种平台能稳定导出真实 usage 后，再考虑内建平台日志适配器；第一版接受标准实验 JSONL。
- 当结构指标表明阅读面明显下降后，再组织人工三分钟理解盲测；盲测结果用于判断可读性，而不是由静态指标代替。
