# 更新 Code-Spec——沉淀可执行契约

当你从调试、实现或讨论中学到有价值的内容时，使用此流程更新相关 code-spec 文档。

**时机**：完成 Task、修复缺陷或发现新模式之后。

---

## Code-Spec 优先规则（关键）

在本项目中，实现工作的 “spec” 指 **code-spec**：
- 可执行契约（而不是只有原则的文字）
- 具体的签名、载荷字段、环境变量键和边界行为
- 可测试的验证/错误行为

### 强制触发条件

变更包含以下任一项时，必须达到 code-spec 深度：
- 新增/变更命令或 API 签名
- 跨层请求/响应契约变更
- 数据库模式/迁移变更
- 基础设施集成（存储、队列、缓存、密钥和环境变量接线）

### 强制输出（7 个部分）

触发后必须包含以下全部内容：
1. 范围 / 触发条件
2. 签名（命令/API/DB）
3. 契约（请求/响应/环境变量）
4. 验证与错误矩阵
5. 良好/基线/错误案例
6. 所需测试（含断言点）
7. 错误与正确示例（至少一组）

---

## 何时更新 Code-Spec

| 触发场景 | 示例 | 目标 Spec |
|---------|------|----------|
| **实现了功能** | 新增集成或模块 | 相关 Spec 文件 |
| **做出设计决策** | 选择可扩展性而非简单性 | 相关 spec + “设计决策”部分 |
| **修复了缺陷** | 发现细微的错误处理问题 | 相关 Spec（如错误处理文档） |
| **发现了模式** | 找到更好的代码组织方式 | 相关 spec 文件 |
| **遇到易踩坑点** | 发现 X 必须先于 Y | 相关 spec + “常见错误”部分 |
| **建立约定** | 团队确定命名模式 | 质量规范 |
| **新增思考触发器** | “做 Y 前别忘了检查 X” | `guides/*.md`（作为检查清单条目） |

**关键洞察**：Code-Spec 更新不只是为了解决问题。每次功能实现都包含未来 AI/开发者安全维护和扩展所需的设计决策与契约。

## Spec 结构概览

```
.trellis/spec/
├── <layer>/           # 各层编码标准（如 backend/、frontend/、api/）
│   ├── index.md       # 概览和链接
│   └── *.md           # 主题规范
└── guides/            # 思考清单（不是编码规范）
    ├── index.md       # 指南索引
    └── *.md           # 主题指南
```

### 关键：区分 Code-Spec 与指南

| 类型 | 位置 | 用途 | 内容风格 |
|------|------|------|----------|
| **Code-Spec（代码规范）** | `<layer>/*.md` | 告诉 AI “如何安全实现” | 签名、契约、矩阵、案例、测试点 |
| **指南（思考指南）** | `guides/*.md` | 帮助 AI 思考“要考虑什么” | 检查清单、问题、指向 Spec 的链接 |

**判断规则**：问自己：

- “这是在说明代码**应该怎么写**” → 放到 spec 层级目录
- “这是在提醒写代码前**要考虑什么**” → 放到 `guides/`

**示例**：

| 学到的内容 | 错误位置 | 正确位置 |
|------------|----------|----------|
| “此 task 使用 API X 而不是 API Y” | ❌ `guides/`（对思考指南过于具体） | ✅ 相关 spec 文件（具体约定） |
| “执行 Y 时记得检查 X” | ❌ Spec 文件（过于抽象） | ✅ `guides/`（思考清单） |

**思考指南应是简短检查清单，并指向 specs**，不要复制详细规则。

## 更新流程

### Step 1：识别学到的内容

回答以下问题：

1. **学到了什么？**（具体说明）
2. **为什么重要？**（能预防什么问题？）
3. **应该放在哪里？**（哪个 spec 文件？）

### Step 2：分类更新类型

| 类型 | 说明 | 操作 |
|------|------|------|
| **设计决策** | 为什么选择 X 而非 Y | 添加到“设计决策”部分 |
| **项目约定** | 本项目如何执行 X | 添加到相关部分并附示例 |
| **新模式** | 新发现的可复用方法 | 添加到“模式”部分 |
| **禁止模式** | 会引发问题的做法 | 添加到“反模式”或“不应使用”部分 |
| **常见错误** | 容易犯的错误 | 添加到“常见错误”部分 |
| **约定** | 已达成一致的标准 | 添加到相关部分 |
| **易踩坑点** | 非显而易见的行为 | 添加警告提示 |

### Step 3：读取目标 Code-Spec

编辑前先读取当前 code-spec，以便：
- 理解现有结构
- 避免重复内容
- 找到正确章节

```bash
cat .trellis/spec/<category>/<file>.md
```

### Step 4：执行更新

遵循以下原则：

1. **具体**：包含明确示例，不要只有抽象规则
2. **解释原因**：说明这样做能预防什么
3. **展示契约**：添加签名、载荷字段和错误行为
4. **展示代码**：关键模式附代码片段
5. **保持简短**：每节只讲一个概念

### Step 5：更新索引（如需要）

如果新增了章节或 code-spec 状态发生变化，请更新分类下的 `index.md`。

## 更新模板

### 基础设施/跨层工作的强制模板

```markdown
## 场景：<名称>

### 1. 范围 / 触发条件
- 触发条件：<为何需要达到 code-spec 深度>

### 2. 签名
- 后端命令/API/DB 签名

### 3. 契约
- 请求字段（名称、类型、约束）
- 响应字段（名称、类型、约束）
- 环境变量键（必需/可选）

### 4. 验证与错误矩阵
- <条件> -> <错误>

### 5. 良好/基线/错误案例
- 良好：...
- 基线：...
- 错误：...

### 6. 所需测试
- 单元测试/集成测试/E2E 及断言点

### 7. 错误与正确示例
#### 错误
...
#### 正确
...
```

### 添加设计决策

```markdown
### 设计决策：[决策名称]

**背景**：我们在解决什么问题？

**考虑过的选项**：
1. 选项 A - 简述
2. 选项 B - 简述

**决策**：我们选择选项 X，因为……

**示例**：
\`\`\`typescript
// 实现方式
代码示例
\`\`\`

**可扩展性**：未来如何扩展……
```

### 添加项目约定

```markdown
### 约定：[约定名称]

**内容**：简述约定。

**原因**：为什么本项目这样做。

**示例**：
\`\`\`typescript
// 如何遵循此约定
代码示例
\`\`\`

**相关内容**：相关约定链接。
```

### 添加新模式

```markdown
### 模式名称

**问题**：解决什么问题？

**解决方案**：简述方法。

**示例**：
\`\`\`
// 良好示例
代码示例

// 错误示例
代码示例
\`\`\`

**原因**：为什么此方法更好。
```

### 添加禁止模式

```markdown
### 不应使用：模式名称

**问题**：
\`\`\`
// 不要这样做
错误代码示例
\`\`\`

**错误原因**：说明问题。

**替代方案**：
\`\`\`
// 应该这样做
良好代码示例
\`\`\`
```

### 添加常见错误

```markdown
### 常见错误：说明

**症状**：会出现什么问题

**原因**：为什么发生

**修复**：如何修正

**预防**：未来如何避免
```

### 添加易踩坑点

```markdown
> **警告**：简述非显而易见的行为。
>
> 说明何时发生以及如何处理。
```

## 交互模式

如果不确定应该更新什么，请回答：

1. **刚刚完成了什么？**
   - [ ] 修复缺陷
   - [ ] 实现功能
   - [ ] 重构代码
   - [ ] 讨论方案

2. **学到或决定了什么？**
   - 设计决策（为什么选 X 而非 Y）
   - 项目约定（我们如何做 X）
   - 非显而易见的行为（易踩坑点）
   - 更好的方法（模式）

3. **未来 AI/开发者是否需要知道？**
   - 为了理解代码如何工作 → 是，更新 spec
   - 为了维护或扩展功能 → 是，更新 spec
   - 为了避免重复错误 → 是，更新 spec
   - 纯一次性实现细节 → 可以跳过

4. **与哪个区域相关？**
   - [ ] 后端代码
   - [ ] 前端代码
   - [ ] 跨层数据流
   - [ ] 代码组织/复用
   - [ ] 质量/测试

## 质量清单

结束 code-spec 更新前确认：

- [ ] 内容是否具体、可执行？
- [ ] 是否包含代码示例？
- [ ] 是否解释了“为什么”，而不只是“做什么”？
- [ ] 是否包含可执行的签名/契约？
- [ ] 是否包含验证与错误矩阵？
- [ ] 是否包含良好/基线/错误案例？
- [ ] 是否包含带断言点的必需测试？
- [ ] 是否位于正确的 code-spec 文件？
- [ ] 是否与现有内容重复？
- [ ] 新团队成员是否能理解？

## 与其他命令的关系

```
开发流程：
  学到内容 → {{CMD_REF:update-spec}} → 知识已沉淀
       ↑                                  ↓
  {{CMD_REF:break-loop}} ←──────────────────── 未来会话受益
  （深度缺陷分析）
```

- `{{CMD_REF:break-loop}}`——深入分析缺陷，通常会发现需要更新的 Spec
- `{{CMD_REF:update-spec}}`——实际执行更新
- `{{CMD_REF:finish-work}}`——提醒你检查是否需要更新 specs

## 核心理念

> **Code-Spec 是活文档。每次调试、每个“恍然大悟”的时刻，都是让实现契约更清晰的机会。**

目标是建立**组织记忆**：
- 一个人学到的内容让所有人受益
- AI 在一次会话中学到的内容能够延续到未来会话
- 错误会转化为有文档记录的防护栏
