# 代码质量检查

对最近编写的代码进行全面质量验证，结合 Spec 合规、跨层安全和提交前检查。

---

## Step 1：识别变更

```bash
git diff --name-only HEAD
git status
```

## Step 2：读取 Task 产物和适用 Spec

按顺序读取当前 Task 产物：

- `prd.md`
- `design.md`（如存在）
- `implement.md`（如存在）

```bash
python3 ./.trellis/scripts/get_context.py --mode packages
```

对每个已变更的包/层，读取 Spec 索引并遵循其 **质量检查** 部分：

```bash
cat .trellis/spec/<package>/<layer>/index.md
```

读取其中引用的具体规范文件——索引是指针，不是终点。

## Step 3：运行项目检查

运行项目的 lint、type-check 和测试命令。修复所有失败后再继续。

## Step 4：按清单审查

### 代码质量

- [ ] lint 工具是否通过？
- [ ] 类型检查器是否通过（如适用）？
- [ ] 测试是否通过？
- [ ] 是否没有遗留调试日志？
- [ ] 是否没有被抑制的警告或类型安全绕过？

### 测试覆盖

- [ ] 新函数 → 是否添加单元测试？
- [ ] 缺陷修复 → 是否添加回归测试？
- [ ] 行为变更 → 是否更新现有测试？

### Spec 同步

- [ ] `.trellis/spec/` 是否需要更新（新模式、约定、经验）？

> “如果我修复了缺陷或发现非显而易见的内容，是否应该记录下来，避免未来再次遇到？”→ 如果答案为“是”，更新相关 Spec 文档。

## Step 5：跨层维度（如适用）

如果变更仅限单层，则跳过此步骤。

### A. 数据流（变更触及 3+ 层）

- [ ] 读取流是否正确：存储 → 服务 → API → 界面
- [ ] 写入流是否正确：界面 → API → 服务 → 存储
- [ ] 类型/模式是否在层间正确传递？
- [ ] 错误是否正确传播给调用方？

### B. 代码复用（修改常量、创建工具函数）

- [ ] 创建新内容前是否搜索了现有类似代码？
  ```bash
  grep -r "pattern" src/
  ```
- [ ] 如果 2+ 位置定义同一值 → 是否提取为共享常量？
- [ ] 批量修改后，所有位置是否都已更新？

### C. 导入/依赖（创建新文件）

- [ ] 导入路径是否正确（相对路径与绝对路径）？
- [ ] 是否没有循环依赖？

### D. 同层一致性

- [ ] 使用同一概念的其他位置是否保持一致？

---

## Step 6：报告并修复

报告发现的违规并直接修复。修复后重新运行项目检查。
