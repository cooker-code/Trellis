# 打破循环——深度缺陷分析

调试完成后，使用此方法进行深入分析，打破“修复缺陷 → 遗忘 → 重复”的循环。

---

## 分析框架

从以下 5 个维度分析刚刚修复的缺陷：

### 1. 根因类别

该缺陷属于哪一类？

| 类别 | 特征 | 示例 |
|------|------|------|
| **A. 缺失 Spec** | 没有说明如何执行的文档 | 新功能没有检查清单 |
| **B. 跨层契约** | 层间接口不清晰 | API 返回格式与预期不同 |
| **C. 变更传播失败** | 修改一处，遗漏其他位置 | 修改函数签名后漏掉调用点 |
| **D. 测试覆盖缺口** | 单元测试通过，集成测试失败 | 单独运行正常，组合后出错 |
| **E. 隐式假设** | 代码依赖未记录的假设 | 时间戳秒与毫秒混淆 |

### 2. 修复为何失败（如适用）

如果成功前尝试过多次修复，请分析每次失败：

- **表面修复**：只修复症状，没有修复根因
- **范围不完整**：找到了根因，但未覆盖所有情况
- **工具限制**：Grep 漏掉了位置，type check 不够严格
- **思维模型**：一直在同一层查找，没有跨层思考

### 3. 预防机制

哪些机制可以防止再次发生？

| 类型 | 说明 | 示例 |
|------|------|------|
| **文档** | 写下来让所有人知道 | 更新思考指南 |
| **架构** | 从结构上让错误无法发生 | 类型安全封装 |
| **编译时** | 严格类型检查，不留例外通道 | 签名变更触发编译错误 |
| **运行时** | 监控、告警、扫描 | 检测孤立实体 |
| **测试覆盖** | E2E 测试、集成测试 | 验证完整流程 |
| **代码审查** | 检查清单、PR 模板 | “是否检查了 X？” |

### 4. 系统性扩展

这个缺陷暴露了哪些更广泛的问题？

- **类似问题**：还有哪些位置可能存在同类问题？
- **设计缺陷**：是否存在根本性的架构问题？
- **流程缺陷**：开发流程是否可以改进？
- **知识缺口**：团队是否缺少某种认知？

### 5. 知识沉淀

将洞察固化到系统：

- [ ] 更新 `.trellis/spec/guides/` 思考指南
- [ ] 更新相关 `.trellis/spec/` 文档
- [ ] 创建问题记录（如适用）
- [ ] 为根因修复创建功能工单
- [ ] 必要时更新检查规范

## 核心理念

> **调试的价值不在于修复这个缺陷，而在于让这一类缺陷永远不再发生。**

三层洞察：
1. **战术层**：如何修复这个缺陷
2. **战略层**：如何预防这一类缺陷
3. **理念层**：如何扩展思考模式

30 分钟的分析可以节省未来 30 小时。

## 思考框架：贝叶斯推理

当存在多个可能的根因且证据不完整时，应根据新证据按比例更新判断，而不是固守最初假设。

### 第 1 步：建立先验概率

调查前，说明你相信什么以及原因：

| 假设 | 先验概率 | 推理 |
|------------|-------|-----------|
| H1：[原因 A] | 40% | 此模式最常见的原因 |
| H2：[原因 B] | 30% | 根据环境判断存在可能 |
| H3：[其他] | 30% | 兜底假设 |

先验概率之和必须为 100%。如果无法分配概率，先进行调查。

### 第 2 步：观察证据

记录实际发现，并明确可靠性：

- 实际观察到了什么？
- 可靠程度如何？（测试输出 > 日志消息 > 用户报告 > 猜测）
- 是否有多个假设可以解释它？

### 第 3 步：更新判断

对每个假设都要问：**如果该假设为真，出现此证据的可能性有多大？**

更新方向比计算更重要：
- H1 强烈预测了该证据 → H1 概率上升
- 证据与 H2 矛盾 → H2 概率下降
- 在所有假设下出现概率相同 → 不更新

### 第 4 步：寻找具有区分度的证据

不要收集更多相同证据。寻找在主要假设之间存在**显著差异**的证据。

> 如果 H1 和 H3 接近：“如果 H1 为真而 H3 不为真，我会看到什么？”然后检查该现象。

### 第 5 步：说明置信度

| 置信度 | 行动 |
|------------|--------|
| 90%+ | 执行修复并监控 |
| 70-90% | 执行修复，并增加回退检查 |
| 50-70% | 提交前先验证假设 |
| <50% | 需要更多证据，不要猜测 |

证据不完整时，绝不要表达非黑即白的确定性。使用“最有可能”“可能但概率较低”“值得调查”等表述。

### 常见谬误

| 谬误 | 示例 | 修正 |
|---------|---------|------------|
| **忽视基础概率** | “测试失败 → 代码损坏” | 测试因其他原因失败的频率是多少？ |
| **确认偏误** | “一定是竞态条件，我去找竞态证据” | 主动寻找反驳首要假设的证据 |
| **锚定效应** | “上次是缓存问题，这次可能还是缓存” | 根据当前上下文建立先验概率，而不是依据昨天的缺陷 |

## 分析后的立即行动

**重要**：完成上述分析后，必须立即执行：

1. **更新 Spec/指南**——不要只列 TODO，要实际更新相关文件：
   - 跨平台问题 → 更新 `cross-platform-thinking-guide.md`
   - 跨层问题 → 更新 `cross-layer-thinking-guide.md`
   - 代码复用问题 → 更新 `code-reuse-thinking-guide.md`
   - 领域特定问题 → 更新 `backend/*.md` 或 `frontend/*.md`

2. **同步模板**——更新 `.trellis/spec/` 后，同步到 `src/templates/markdown/spec/`

3. **提交 spec 更新**——这是主要产出，不是聊天中的分析文本

> **如果分析只留在聊天里，它毫无价值。价值来自更新后的 specs。**
